# erp-assistant

Builder visual de SQL Oracle, local e dev-only, que roda consultas no Sankhya (ERP) via `DbExplorerSP.executeQuery`; as credenciais ficam no servidor Next.js. Escopo e decisões: leia [`SPEC.md`](SPEC.md) antes de criar ou mudar qualquer feature.

## Regras

- **Local-only é o requisito central.** Preserve cada proteção listada em "Proteções" no `SPEC.md`; qualquer mudança que enfraqueça uma delas precisa de confirmação explícita minha.
- **Credenciais e bearer token ficam só no servidor**: todo arquivo em `src/features/*/server/` e `src/lib/db/` começa com `import "server-only"`, e nada que as rotas devolvem ou registram em log contém esses valores (use `redactText`/`redactHeaders`).
- **Features que você escrever só leem dados do ERP.** Se uma tarefa pedir chamada que grave (`save`, `insert`, `update`, `delete`, ações que alterem dados), pare e pergunte.
- `src/app/` é só roteamento: cada `route.ts` reexporta o handler de `src/features/<feature>/server/`. A lógica fica nas features (`src/features/`) e no que é compartilhado (`src/lib/`, `src/components/`).
- `src/lib/sql/` só usa `import type` entre seus arquivos, para rodar direto no Node (`node arquivo.mjs` importando os `.ts`) ao verificar o gerador e a trava de leitura.
- Interface com shadcn/ui (preset `base-nova`, sobre Base UI: use `render`, não `asChild`), com os componentes em `src/components/ui/` (adicione com `pnpm dlx shadcn@latest add <nome>` e consulte a API pelo context7). Cores e bordas pelos tokens do tema (`bg-card`, `text-muted-foreground`, `border-border`, `text-destructive`...), não `zinc-*`; Tailwind para o layout e a classe `.label` de `src/app/globals.css` para títulos de seção. Escolhas únicas usam o `OptionMenu` (`src/components/option-menu.tsx`, no estilo do menu ƒ; aceita `variant`, `icon`, `placeholder`...), não `<select>` nativo; mantenha o autocomplete em Downshift (`src/components/combobox.tsx`) e a tabela de resultados em TanStack Table/Virtual (sem o `Table` do shadcn).
- Avisos, erros e confirmações aparecem como toasts do `sonner` (`toast.error`/`warning`/`success`, com `id` fixo nos que podem se repetir); o `Toaster` fica em `explorer.tsx`. O erro da consulta fica só no painel de resultado e a validação em tempo real (trava de leitura, problemas do gerador) fica inline.
- Dependências novas além de next, react, tailwind, zod, TanStack Table/Virtual, `@dnd-kit/react`, `downshift`, `lucide-react`, shadcn (`@base-ui/react`, `class-variance-authority`, `cn`, `tw-animate-css`, `shadcn`, `@shadcn/react`, `shiki`), `sonner`, `@uiw/react-codemirror`, `@codemirror/lang-sql` e `prettier` (dev): pergunte antes. O agente de IA autoriza também `ai` (Vercel AI SDK) com `ollama-ai-provider-v2`, a extensão `pgvector` e, só na fase 4, `@ai-sdk/google`; ele fica em `src/features/assistant` (`/api/assistant/*`), não em `ai`. Índice do dicionário em `AiDocument`/`AiIndex` (SQL cru parametrizado; colunas só sob demanda). `pnpm test:ai` roda os testes de `src/lib/ai/` (só `import type` entre eles, como em `lib/sql`); `pnpm ai:export`/`ai:import` levam o índice entre máquinas; `pnpm ai:pull-chat`/`ai:pull-embed` baixam os modelos com `ollama pull` dentro do container `ollama` (o compose não tem serviço de pull). Config por `AI_PRESET=gpu|cpu`; o Ollama só em `127.0.0.1:11434`; `COMPOSE_FILE` escolhe `compose.gpu.yaml` (desktop) ou só `compose.yaml` (notebook). O TanStack Table é v9 (`useTable` + `tableFeatures`, não a API v8 `useReactTable`); consulte a documentação dele pelo context7.
- Roda com `docker compose up` ou `pnpm dev` (só em `127.0.0.1:3100`; nunca troque o hostname). O banco é o Postgres do compose, configurado pelo `.env` (copie de `.env.example`); o `pnpm dev` precisa dele no ar (`docker compose up -d postgres`). `pnpm seed` cria o perfil padrão a partir das `SANKHYA_PROFILE_*` do `.env` (opcional; nunca o rode nem leia esses valores na verificação, pois são credenciais reais). Mudou o `schema.prisma`: crie uma migration em `prisma/migrations/` (conversões de coluna levam `USING`, nunca DROP/ADD). Formatação com Prettier (`.prettierrc.json`: aspas duplas, `;`, vírgula final, 120 colunas): rode `pnpm format` antes de commitar (`pnpm format:check` só confere); `src/components/ui/` (shadcn), `*.md`, o código gerado do Prisma e as migrations ficam fora (`.prettierignore`). Para checar tipos: `pnpm typecheck`; para o gerador e a trava de leitura: `pnpm test:sql`.
- **Verificação contra um Sankhya falso**: os perfis do usuário têm credenciais reais. Suba um projeto separado com um override que publica em outra porta, porque a instância do usuário pode estar ocupando a 3100 (`ports: !override ["127.0.0.1:3101:3100"]`): `docker compose -p snk-verify -f compose.yaml -f <override> up -d --force-recreate`. Ele usa um volume `pgdata` próprio (sem os perfis reais) e lê o mesmo `.env`; o override também precisa mudar a porta do Postgres (`postgres: ports: !override ["127.0.0.1:5433:5432"]`): cadastre nele um perfil apontando para o Sankhya falso e confirme `baseUrl` em `/api/sankhya/status` antes de qualquer requisição. Com `pnpm dev`, o banco é o Postgres do compose do usuário (mesmos perfis reais); não ative um perfil real durante a verificação.
